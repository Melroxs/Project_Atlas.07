Atlas Repository Structure & Development Environment Specification (Version 1.0)1. PurposeThis document defines the standard structure, tooling, and development workflow for Atlas. Every contributor and every AI coding assistant should follow this specification to ensure the codebase remains consistent, maintainable, and scalable.2. Repository PhilosophyAtlas will be developed as a modular TypeScript application with a clear separation between presentation, business logic, data access, AI services, and infrastructure.Core principles:One responsibility per module.No duplicated business logic.Shared types across frontend and backend.API-first architecture.Strong typing throughout.Feature-based organization where appropriate.Clear boundaries between layers.3. Recommended Repository Structureatlas/│├── apps/│   └── web/                    # Next.js application│├── packages/│   ├── ui/                     # Shared UI components│   ├── types/                  # Shared TypeScript types│   ├── config/                 # Shared configuration│   ├── utils/                  # Shared utilities│   └── ai/                     # Shared AI logic│├── docs/                       # Technical documentation│├── database/│   ├── schema/│   ├── migrations/│   └── seed/│├── scripts/                    # Development scripts│├── tests/│   ├── unit/│   ├── integration/│   └── e2e/│├── public/│└── .github/    └── workflows/4. Frontend StructureWithin the Next.js application:app/components/features/hooks/lib/services/styles/types/middleware/Responsibilitiesapp/RoutesLayoutsPagescomponents/Reusable UI components onlyfeatures/Business featuresClaimsDocumentsSupplementsDashboardSettingshooks/Custom React hooksservices/API communicationAuthenticationAI clientStorage clientlib/HelpersValidationUtilities5. Backend Structureapi/services/repositories/middleware/validators/jobs/ai/Responsibilitiesapi/HTTP endpoints onlyservices/Business logicrepositories/Database accessvalidators/Request validationmiddleware/AuthenticationAuthorizationLoggingjobs/Background processingai/AI workflowsPrompt templatesStructured output parsers6. Database Structuredatabase/│├── schema/├── migrations/├── seed/├── views/└── functions/7. Documentation StandardsEvery major feature should include:PurposeRequirementsArchitectureAPI specificationDatabase changesUser flowTesting strategyFuture improvements8. Environment ConfigurationSeparate configuration files for:Local developmentTestingStaging (future)ProductionNo secrets should ever be committed to source control.9. Coding StandardsNamingComponents:PascalCaseFunctions:camelCaseVariables:camelCaseConstants:UPPER_SNAKE_CASEDatabase tables:snake_caseAPI routes:kebab-case10. Error HandlingEvery error should:Be logged.Return a consistent API response.Avoid exposing sensitive information.Include a trace identifier where applicable.11. Logging StandardsLog:Authentication eventsAI requestsAI responses (sanitized if needed)ErrorsDatabase failuresBackground jobsUser actions relevant to auditing12. Testing StrategyEach module should include:Unit testsIntegration testsEnd-to-end tests (for critical workflows)Critical user journeys—such as claim creation, document upload, supplement generation, and package export—must have end-to-end coverage before a production release.13. Git WorkflowSuggested branch strategy:main – production-ready codedevelop – integration branchfeature/<feature-name> – new featuresbugfix/<issue-name> – fixeshotfix/<issue-name> – urgent production fixesPull requests should:Focus on a single feature or fix.Pass automated checks.Include updated documentation if behavior changes.14. Definition of DoneA feature is considered complete only when:Requirements are implemented.Code follows project standards.Tests pass.Documentation is updated.Security and validation checks are in place.Code review is completed.15. Documentation RoadmapFrom here, we'll build a complete engineering specification for Atlas in this order:✅ System Architecture Specification✅ Repository Structure & Development EnvironmentDatabase Architecture & Data ModelAuthentication & AuthorizationAPI SpecificationFrontend ArchitectureClaims Management ModuleDocument Management ModulePhoto Management ModuleAI Decision EngineSupplement Generation EngineCompliance Validation EngineReporting & AnalyticsNotifications & Background JobsSecurity & Audit LoggingTesting StrategyDeployment & OperationsMVP Demo & Production ReadinessThis sequence gives us a complete blueprint before implementation, making the build more predictable and allowing us to tackle one well-defined subsystem at a time.
