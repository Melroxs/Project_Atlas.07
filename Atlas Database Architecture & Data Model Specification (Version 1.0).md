Atlas Database Architecture & Data Model Specification (Version 1.0)1. PurposeThis document defines the database architecture for Atlas, including core entities, relationships, naming standards, indexing strategy, migrations, and data integrity rules. The database is the single source of truth for all operational data.2. Database PhilosophyAtlas will use a relational PostgreSQL database designed around normalized data with clear relationships, while allowing JSON fields only where flexibility is beneficial (such as AI metadata or extracted document information).Core principles:Normalize operational data.Enforce referential integrity with foreign keys.Prefer explicit relationships over duplicated data.Use transactions for multi-step operations.Soft-delete business records where auditability is required.Maintain complete audit trails for important actions.3. Relationship StandardsExamples:One Organization → Many UsersOne Organization → Many ClaimsOne Claim → Many DocumentsOne Claim → Many PhotosOne Claim → Many SupplementsOne Supplement → Many Line ItemsOne Line Item → Many Evidence LinksOne Claim → Many AI DecisionsOne Claim → Many Timeline Events7. Naming ConventionsTables:snake_caseplural names (e.g., claims, documents, supplement_items)Columns:snake_casePrimary Keys:idForeign Keys:<entity>_idTimestamps:created_atupdated_atdeleted_at (for soft deletes where applicable)8. Indexing StrategyIndexes should be created for:Primary keysForeign keysFrequently searched claim numbersEmail addressesStatus fieldsCreation datesFull-text search on extracted document content (where appropriate)The goal is to optimize common workflows such as searching claims, filtering by status, and retrieving related documents efficiently.9. Migration StrategyDatabase changes should:Be version-controlled.Use incremental migrations.Avoid destructive changes without a rollback plan.Include data migrations where schema changes require transformations.10. Seed DataDevelopment and demo environments should include realistic seed data for:OrganizationsUsersCustomersClaimsDocumentsPhotosSupplementsAI recommendationsCompliance outcomesThis ensures every feature can be demonstrated consistently without manual setup.11. Future ExpansionThe schema should allow for future additions without major redesign, including:Multi-office organizationsMultiple insurance carriers per claimContractor subcontractor managementIntegrations with estimating platformsCRM integrationsCalendar and schedulingVoice assistant memoryWorkflow automationPredictive analytics12.
