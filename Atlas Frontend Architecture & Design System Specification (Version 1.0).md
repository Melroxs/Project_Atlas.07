PurposeThis specification defines the frontend architecture for Atlas, including application structure, routing, layouts, component standards, state management, design system, accessibility, and responsive behavior.The goal is to ensure every interface is intuitive, consistent, and scalable.---# 2. Frontend PhilosophyAtlas should feel like a professional operations platform rather than a collection of disconnected pages.Core principles:* Consistency over novelty.* Fast and responsive interactions.* Minimal clicks to complete common tasks.* AI assists users but never obscures important information.* Accessibility is built in from the start.* Mobile support for field users without sacrificing desktop productivity.---# 3. Technology Stack## Framework* Next.js (App Router)## Language* TypeScript## UI Library* React* shadcn/ui## Styling* Tailwind CSS## Icons* Lucide React## Forms* React Hook Form* Zod validation## Tables* TanStack Table## Charts* Recharts---# 4. Application Structure```textapp/components/features/hooks/lib/services/styles/types/```### Responsibilities**app/*** Routes* Layouts* Authentication gates**components/*** Generic reusable UI**features/*** Business modules* Claims* Documents* Photos* AI* Supplements* Compliance**hooks/*** Shared React hooks**services/*** API communication* Authentication* AI client**lib/*** Utilities* Formatting* Validation helpers---# 5. Routing StructureCore routes include:* `/login`* `/dashboard`* `/claims`* `/claims/[id]`* `/documents`* `/photos`* `/supplements`* `/ai`* `/reports`* `/notifications`* `/settings`* `/admin`Each feature should own its routes and related components.---# 6. Layout System### Public Layout* Landing page* Authentication pages### Authenticated Layout* Top navigation* Left sidebar* Main content area* Notification center* User menu### Full-Screen WorkspaceFor focused workflows such as:* AI Interview* Document Review* Supplement Builder---# 7. NavigationPrimary navigation:* Dashboard* Claims* Documents* Photos* Supplements* AI Workspace* Reports* Notifications* SettingsNavigation should remain predictable and consistent across the application.---# 8. Design System## TypographyHierarchy should clearly distinguish:* Page titles* Section headings* Card titles* Body text* CaptionsTypography should prioritize readability over decorative styling.---## Color SystemSemantic color roles:* Primary* Secondary* Success* Warning* Error* Information* NeutralColors should communicate meaning consistently, particularly for claim status and compliance results.---## SpacingUse a consistent spacing scale for:* Margins* Padding* Grid gaps* Section separationAvoid arbitrary spacing values.---## ElevationUse subtle elevation to distinguish:* Cards* Dialogs* Drawers* Floating AI assistant* Dropdown menus---# 9. Component StandardsReusable components should include:* Buttons* Inputs* Select menus* Text areas* Checkboxes* Radio buttons* Tables* Cards* Modals* Drawers* Tabs* Badges* Tooltips* Toast notifications* Loading indicatorsEach component should support:* Disabled state* Loading state* Error state* Keyboard navigation---# 10. FormsForms should:* Validate on submission and optionally during input.* Display clear error messages.* Preserve entered data where practical.* Prevent duplicate submissions.* Provide loading indicators during processing.---# 11. TablesTables should support:* Sorting* Filtering* Search* Pagination* Column resizing (future)* Export (where applicable)Claims, documents, users, and supplements should all follow a common table pattern.---# 12. Dashboard StandardsThe dashboard should provide at-a-glance visibility into:* Active claims* Claims awaiting action* Revenue recovered* Pending supplements* Compliance alerts* AI processing queue* Recent activityUsers should be able to drill down into each metric.---# 13. Claim WorkspaceThe claim page is the heart of Atlas.It should include:* Claim summary* Customer information* Property details* Documents* Photos* Activity timeline* AI recommendations* Supplement workspace* Compliance panel* Notes and tasksThe goal is to minimize navigation away from the claim while working.---# 14. AI WorkspaceThe AI workspace should clearly distinguish between:* User-provided information.* AI-generated recommendations.* Confidence scores.* Supporting evidence.* Required human review.AI outputs should always be explainable and linked to evidence.---# 15. NotificationsNotifications should be categorized by priority, such as:* Information* Warning* Action required* System alertsUsers should be able to mark notifications as read and navigate directly to the related record.---# 16. Responsive Design### DesktopPrimary environment for office users with multi-panel layouts and dense information.### TabletOptimized for supervisors and field managers with simplified layouts.### MobileFocused on essential tasks:* View claims* Upload photos* Upload documents* Review notifications* Update claim statusComplex editing workflows can remain desktop-first in the MVP.---# 17. AccessibilityAtlas should meet modern accessibility expectations by providing:* Full keyboard navigation.* Sufficient color contrast.* Descriptive labels for form controls.* Screen reader support.* Visible focus indicators.* Error messages that are announced appropriately.Accessibility should be treated as a core requirement, not an enhancement.---# 18. PerformanceFrontend goals:* Fast initial page load.* Lazy-load large feature modules where appropriate.* Optimize image delivery.* Minimize unnecessary re-renders.* Cache frequently used data responsibly.Users should perceive the application as responsive, even when AI tasks are running in the background.---# 19. Future EnhancementsThe architecture should support future additions, including:* Dark mode.* Multiple dashboard layouts.* Customizable widgets.* Offline support for field users.* Voice-controlled navigation.* Real-time collaboration.* Multi-language support.---# 20. Acceptance CriteriaThe frontend architecture is complete when:* Navigation is consistent across the application.* Reusable components are used throughout.* Responsive layouts work across supported devices.* Forms, tables, and dashboards follow shared patterns.* Accessibility standards are met.* Performance targets are achieved.* AI interactions are integrated seamlessly into user workflows.---# Documentation ProgressWe have now documented the core platform foundation:* ✅ System Architecture* ✅ Repository Structure & Development Environment* ✅ Database Architecture & Data Model* ✅ Authentication & Authorization* ✅ API Architecture & Service Layer* ✅ Frontend Architecture & Design System## Next Document: Claims Management ModuleThis will be the first feature-level specification and will define the complete lifecycle of an insurance claim within Atlas, including claim creation, status transitions, assignments, notes, tasks, documents, photos, AI analysis, supplement workflow, compliance checks, and activity tracking.
