Atlas API Architecture & Service Layer Specification (Version 1.0)1. PurposeThis specification defines the API architecture, service boundaries, request and response standards, validation rules, and coding patterns for Atlas.The API layer serves as the contract between the frontend, backend services, AI engine, and external integrations.2. API Design PrinciplesEvery Atlas API should follow these principles:RESTful design for the MVP.Stateless requests.Consistent naming conventions.JSON request and response bodies.Strong input validation.Clear error handling.Idempotent operations where applicable.Version-ready architecture.3. High-Level Request FlowBrowser   │   ▼Next.js Route Handler   │   ▼Authentication Middleware   │   ▼Authorization Middleware   │   ▼Input Validation   │   ▼Business Service   │   ▼Repository Layer   │   ▼DatabaseFor AI-related requests:Client   │   ▼API Route   │   ▼Business Service   │   ▼AI Service   │   ▼LLM / OCR Provider   │   ▼Structured Response   │   ▼Business Service   │   ▼Database4. Layer ResponsibilitiesRoute HandlersResponsible for:Receiving HTTP requests.Authentication.Authorization.Calling validators.Invoking business services.Returning responses.Route handlers must not contain business logic.Validation LayerResponsible for:Required fields.Data types.Field length.Formats.Business rule pre-checks.Invalid requests should never reach the business service layer.Business ServicesResponsible for:Business rules.Workflow orchestration.Transactions.AI orchestration.Notifications.Audit logging.Business services should remain independent of HTTP concepts.Repository LayerResponsible for:Reading data.Writing data.Database queries.Pagination.Filtering.Transactions.Repositories should not implement business rules.AI Service LayerResponsible for:Prompt construction.Model selection.Response parsing.Confidence scoring.Retry handling.AI provider abstraction.This separation makes it easier to replace AI providers in the future.5. API ModulesThe MVP API will include:AuthenticationExamples:Sign inSign outRefresh sessionCurrent userPassword resetOrganizationsExamples:Get organizationUpdate organizationList usersInvite userClaimsExamples:Create claimUpdate claimSearch claimsGet claimArchive claimCustomersExamples:Create customerUpdate customerSearch customersPropertiesExamples:Create propertyUpdate propertyDocumentsExamples:UploadReplaceOCR statusSearchPhotosExamples:UploadTagDeleteAI analysisSupplementsExamples:GenerateSave draftSubmit for reviewApproveExportAIExamples:InterviewAnalyze claimGenerate recommendationsEvaluate evidenceComplianceExamples:Validate supplementRun compliance checkView findingsReportsExamples:Dashboard metricsRevenue recoveredClaim summariesActivity reports6. URL StandardsExamples:/api/v1/auth/api/v1/claims/api/v1/documents/api/v1/photos/api/v1/supplements/api/v1/complianceEven if only one version exists initially, the API should be structured to support future versioning.7. Request StandardsAll requests should:Use JSON unless uploading files.Validate required fields.Reject unknown or malformed data where appropriate.Include authentication for protected routes.File uploads should use multipart form data.8. Response StandardsEvery successful response should follow a consistent structure, for example:{  "success": true,  "data": {},  "meta": {}}Every error response should include:Success status.Error code.Human-readable message.Optional validation details.Trace identifier for diagnostics.9. Pagination StandardList endpoints should support:Page number.Page size.Sorting.Filtering.Search.Responses should include pagination metadata such as total records and total pages.10. FilteringCommon filters:Claims:StatusAssigned userDate rangeCarrierDocuments:TypeProcessing statusUpload dateSupplements:StatusConfidence scoreReviewer11. Validation StandardsValidation occurs before business logic.Examples:Claim creation:Claim number required.Organization required.Valid customer reference.Valid property reference.Document upload:Supported file type.Maximum file size.Valid claim reference.Supplement generation:Claim exists.Required evidence present.Documents processed.12. Error CategoriesExamples include:Authentication errors.Authorization errors.Validation failures.Resource not found.Conflict errors.AI processing failures.External service failures.Internal server errors.Each category should map to appropriate HTTP status codes and standardized error codes.13. Background OperationsSome API requests should return immediately while work continues in the background.Examples:OCR processing.AI document analysis.Supplement generation.Report generation.Notification delivery.Clients should be able to check the processing status.14. API Documentation RequirementsEach endpoint should document:Purpose.Authentication requirements.Required permissions.Request format.Response format.Error responses.Example requests.Example responses.15. Service BoundariesEach business service should own a single domain.Examples:Claim Service.Document Service.Photo Service.Supplement Service.AI Service.Compliance Service.Notification Service.Reporting Service.Services should communicate through defined interfaces rather than directly depending on each other's internal implementation.16. Future Integration PointsThe API architecture should support future integrations with:Estimating platforms.CRM systems.Accounting software.Calendar providers.Email providers.SMS gateways.Cloud storage providers.Voice assistant services.External integrations should be isolated behind dedicated integration services.17. Acceptance CriteriaThe API layer is complete when:Every module exposes documented endpoints.Input validation is consistent.Business logic resides only in services.Database access is isolated to repositories.Responses follow a common format.Errors are standardized.Background jobs are supported.Endpoints are fully documented.Documentation ProgressWe have now established the core engineering foundation:✅ System Architecture Specification✅ Repository Structure & Development Environment✅ Database Architecture & Data Model✅ Authentication & Authorization Architecture✅ API Architecture & Service LayerNext DocumentThe next specification should be Frontend Architecture & Design System.
