Atlas Authentication & Authorization Architecture Specification (Version 1.0)1. PurposeThis document defines how Atlas authenticates users, authorizes access to data, and protects customer information. The design follows the principle of least privilege, ensuring users only access the data and actions required for their role.2. Security PrinciplesAtlas will be built on these core principles:Authentication before authorization.Every request is verified.Multi-tenant isolation by default.Role-Based Access Control (RBAC).Principle of least privilege.Complete audit logging of security-sensitive actions.Secure session management.Encryption of sensitive data in transit and at rest.3. Authentication FlowThe MVP will use Supabase Authentication as the identity provider.Typical flow:User   │   ▼Login Screen   │   ▼Supabase Authentication   │   ▼Session Created   │   ▼Atlas API   │   ▼Permission Validation   │   ▼Requested Resource4. Identity ModelEach authenticated user belongs to exactly one organization in the MVP.Core entities:UserOrganizationRoleSessionEvery authenticated request includes:User IDOrganization IDRoleSession identifierThis ensures all data access is scoped to the correct organization.5. Multi-Tenant ArchitectureAtlas is designed as a multi-tenant application.Every business record is associated with an organization_id.Examples:ClaimsDocumentsPhotosSupplementsAI DecisionsAudit LogsNotificationsUsers must never be able to access records belonging to another organization.6. Role-Based Access Control (RBAC)Initial MVP roles:System AdministratorManage platform configuration.Access all organizations (internal use only).Organization AdministratorManage users.Configure organization settings.View all organization data.Operations ManagerManage claims.Assign work.Review reports.Supplement SpecialistCreate and edit supplements.Generate AI recommendations.Submit for review.Project ManagerManage assigned claims.Upload documents and photos.Review claim progress.Office AdministratorManage customer information.Upload supporting documents.Coordinate communications.Read-Only UserView authorized records only.No editing permissions.7. Permission ModelPermissions are action-based rather than page-based.Examples:ClaimsViewCreateUpdateArchiveDocumentsUploadViewReplaceDeletePhotosUploadTagDeleteSupplementsGenerateEditApproveExportAdministrationInvite usersRemove usersManage rolesUpdate organization settingsThis approach makes it easier to extend permissions as Atlas grows.8. Authorization PipelineEvery API request follows this sequence:Request   │   ▼Authentication   │   ▼Session Validation   │   ▼Organization Check   │   ▼Role Check   │   ▼Permission Check   │   ▼Business Logic   │   ▼Database AccessIf any step fails, the request is rejected with an appropriate error response.9. Session ManagementSessions should:Be securely stored.Expire after inactivity.Be refreshable without requiring frequent logins.Be revocable by administrators.Be invalidated upon password changes or account suspension.10. Password & Identity PoliciesFor users authenticated with email and password:Strong password requirements.Password reset via secure email link.Email verification before account activation.Protection against repeated failed login attempts.Future enhancements may include:Multi-factor authentication (MFA).Single Sign-On (SSO).Enterprise identity providers.11. Data ProtectionSensitive data should be encrypted where appropriate.Examples include:Personal contact information.Access tokens.Session identifiers.API secrets.AI provider credentials.TLS should be used for all network communication.12. Audit LoggingSecurity-sensitive events must be recorded.Examples:Authentication:Successful login.Failed login.Logout.Password reset.Session expiration.Administration:User created.User deleted.Role changed.Permission updated.Claims:Claim ownership changed.Supplement approved.Compliance override.Document deletion.Audit logs should be immutable and retained according to organizational policy.13. API SecurityEvery protected endpoint should:Require authentication.Validate organization ownership.Check required permissions.Validate input.Log significant actions.Return standardized error responses.Public endpoints should be limited to:Login.Password reset.Health checks (if required).14. Security Headers & Web ProtectionsThe application should enforce:HTTPS only.Secure cookies.Protection against common web attacks (such as cross-site scripting and cross-site request forgery where applicable).Appropriate Content Security Policy (CSP).Rate limiting on authentication and sensitive endpoints.15. Future EnhancementsThe authentication system should be designed to support future capabilities, including:Multi-factor authentication (MFA).Single Sign-On (Microsoft, Google, Okta, etc.).Delegated access for external adjusters.Temporary guest access.API keys for integrations.Service accounts for automation.16. Acceptance CriteriaThe authentication and authorization layer is considered complete when:Users can securely sign in and sign out.Every request is authenticated.Organization data is fully isolated.Role-based permissions are enforced.Unauthorized access is prevented.Security events are logged.Sessions are managed securely.Sensitive information is protected.Next Document: API Architecture & Service Layer SpecificationThis document will define how every module communicates through APIs.
