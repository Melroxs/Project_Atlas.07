# PLAT-004 — Atlas Error Handling Framework**Document ID:** PLAT-004**Version:** 1.0**Status:** Draft**Owner:** Atlas Engineering**Depends On:**- PLAT-001 Authentication Architecture- PLAT-002 Authorization & RBAC- PLAT-003 Multi-Tenant Architecture---# PurposeThis document defines the standard error handling architecture for Atlas.The goal is to ensure that every failure across:- API- Database- AI systems- Voice systems- Background jobs- Integrationsis handled consistently, securely, and observably.---# Error Handling PrinciplesAtlas errors must be:- Predictable.- Typed.- Logged.- Secure.- Actionable.- User-friendly.Errors must never expose:- Database internals.- Secrets.- Infrastructure details.- Private tenant information.---# Error FlowAll errors follow:```Application Event        |Error Created        |Error Classified        |Logged        |Mapped        |Response Returned```---# Error CategoriesAtlas uses six primary error categories.---# 1. Validation ErrorsPurpose:Invalid input from users or external systems.Examples:- Missing required field.- Invalid email.- Incorrect document format.- Invalid claim status transition.Code:```VALIDATION_ERROR```HTTP:```400 Bad Request```Example:```json{ "code":"VALIDATION_ERROR", "message":"Claim number is required"}```---# 2. Authentication ErrorsPurpose:Identity verification failures.Examples:- Invalid password.- Expired session.- Invalid token.Code:```AUTHENTICATION_ERROR```HTTP:```401 Unauthorized```---# 3. Authorization ErrorsPurpose:User authenticated but not allowed.Examples:- User cannot approve supplements.- User cannot access another department.Code:```FORBIDDEN_ERROR```HTTP:```403 Forbidden```---# 4. Resource ErrorsPurpose:Requested entity unavailable.Examples:- Claim not found.- Document deleted.- Organization missing.Codes:```RESOURCE_NOT_FOUNDRESOURCE_CONFLICT```HTTP:```404409```---# 5. Business Logic ErrorsPurpose:Rules prevent an action.Examples:- Cannot submit incomplete supplement.- Cannot close claim without required evidence.- Cannot approve AI recommendation.Codes:```BUSINESS_RULE_ERROR```HTTP:```422 Unprocessable Entity```---# 6. System ErrorsPurpose:Unexpected technical failures.Examples:- Database unavailable.- External API failure.- AI provider timeout.Code:```INTERNAL_ERROR```HTTP:```500 Internal Server Error```---# Standard Error ObjectAll Atlas errors follow:```typescript{ code: string; message: string; details?: unknown; requestId: string; timestamp: Date;}```---# Domain Error ClassesAtlas should use typed errors.Example:```typescriptclass OrganizationNotFoundErrorextends AtlasError { code = "ORGANIZATION_NOT_FOUND"; statusCode = 404;}```---# Required Domain Errors## Organization```ORGANIZATION_NOT_FOUNDDUPLICATE_ORGANIZATIONORGANIZATION_ARCHIVED```---## Claims```CLAIM_NOT_FOUNDINVALID_CLAIM_STATUSCLAIM_ACCESS_DENIED```---## Documents```DOCUMENT_NOT_FOUNDDOCUMENT_PROCESSING_FAILEDUNSUPPORTED_DOCUMENT_TYPE```---## AI```AI_CONTEXT_MISSINGAI_GENERATION_FAILEDAI_PERMISSION_DENIED```---## Voice```VOICE_SESSION_FAILEDVOICE_COMMAND_NOT_ALLOWEDVOICE_ACTION_REQUIRES_APPROVAL```---# API Error HandlingControllers should not manually format errors.Flow:```Controller↓Throws Domain Error↓Global Error Middleware↓Standard API Response```---# Frontend Error HandlingThe UI should classify errors:## User Action ErrorsExample:"Your supplement is missing required evidence."Action:Show guidance.---## System ErrorsExample:"Atlas is temporarily unavailable."Action:Retry or contact support.---# AI Error HandlingAI errors require additional handling.Examples:## Low ConfidenceNot an error.Result:```NEEDS_REVIEW```---## Missing EvidenceResult:```INSUFFICIENT_INFORMATION```---## AI FailureResult:```AI_SERVICE_UNAVAILABLE```Human workflows must continue.---# Voice Error HandlingVoice responses must be conversational.Instead of:```ERROR 403```Atlas says:"Your account does not have permission to perform that action."---# Logging RequirementsEvery error log must include:```requestIdorganizationIduserIderrorCodetimestampstackTrace```---# Monitoring RequirementsTrack:- Error frequency.- Failed workflows.- AI failures.- Integration failures.- Authentication failures.---# Retry RulesAutomatic retries allowed for:- Network failures.- Temporary provider failures.- Queue failures.No retry for:- Validation errors.- Permission errors.- Business rule errors.---# Security RequirementsNever log:- Passwords.- Tokens.- API keys.- Sensitive claim documents.- Personal information unnecessarily.---# Acceptance CriteriaThe error framework is complete when:- All services use typed errors.- API responses are standardized.- Errors are logged.- Sensitive information is protected.- AI and voice failures degrade gracefully.- Developers can quickly diagnose problems.---# Next Document**PLAT-005 — Audit Logging & Observability Framework**This document will define how Atlas records
