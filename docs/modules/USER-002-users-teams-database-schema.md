# USER-002 — Atlas Users & Teams Database Schema**Document ID:** USER-002**Version:** 1.0**Status:** Draft**Owner:** Atlas Engineering**Depends On:**- USER-001 Users & Teams Architecture- PLAT-003 Multi-Tenant Architecture- PLAT-005 Audit Logging Framework---# PurposeThis document defines the database architecture for Atlas users and teams.The schema supports:- Multi-tenant user management.- Role assignment.- Team organization.- Invitations.- User preferences.- AI personalization context.---# Database Design PrinciplesThe user system follows:- Every user belongs to an organization.- Every record is tenant isolated.- Users are soft-deletable.- All changes are auditable.- Permissions are managed separately through RBAC.---# Entity Relationship Overview```Organization     |     | Users     |  Teams     |Team MembersUsers     |User PreferencesOrganizations     |User Invitations```---# Table 1 — usersPrimary user identity table.## PurposeStores people who access Atlas.---## Schema```usersidorganization_idfirst_namelast_nameemailphoneavatar_urlstatuslast_login_atcreated_atupdated_atdeleted_atcreated_byupdated_by```---# Field Definitions| Field | Type | Description ||-|-|-|| id | UUID | User identifier || organization_id | UUID | Tenant owner || first_name | VARCHAR | User first name || last_name | VARCHAR | User surname || email | VARCHAR | Login email || phone | VARCHAR | Contact number || avatar_url | TEXT | Profile image || status | ENUM | User lifecycle state || last_login_at | TIMESTAMP | Last login || created_at | TIMESTAMP | Creation date || updated_at | TIMESTAMP | Last update || deleted_at | TIMESTAMP | Soft deletion |---# User Status Enum```INVITEDACTIVESUSPENDEDDEACTIVATED```---# IndexesRequired:```users_email_idxusers_organization_idxusers_status_idx```---# Table 2 — teamsPurpose:Organize users operationally.---## Schema```teamsidorganization_idnamedescriptioncreated_atupdated_atcreated_byupdated_bydeleted_at```---# Example Data```Team:Estimating DepartmentTeam:Production OperationsTeam:Administration```---# Table 3 — team_membersPurpose:Many-to-many relationship between users and teams.---## Schema```team_membersidorganization_idteam_iduser_idrole_labeljoined_atcreated_at```---# Relationship```User  |  | many  |Teams```---# ConstraintsRequired:```unique(team_id,user_id)```A user cannot be added to the same team twice.---# Table 4 — user_invitationsPurpose:Manage onboarding.---## Schema```user_invitationsidorganization_idemailrole_idtokenstatusexpires_ataccepted_atcreated_atcreated_by```---# Invitation Status```PENDINGACCEPTEDEXPIREDCANCELLED```---# Security RequirementsInvitation tokens must:- Be randomly generated.- Expire.- Never be stored in plain text.---# Table 5 — user_preferencesPurpose:Store personalization settings.---## Schema```user_preferencesidorganization_iduser_iddashboard_preferencesnotification_preferencesai_preferencesvoice_preferencescreated_atupdated_at```---# AI Preference Examples```json{ "responseStyle":"brief", "preferredAssistantName":"Atlas", "autoSummaries":true}```---# Voice Preference Examples```json{ "voiceEnabled":true, "wakeWord":"Atlas", "responseSpeed":"normal"}```---# Tenant IsolationEvery table requires:```organization_id```Queries must always filter by:```currentOrganizationId```---# Security Rules## UsersUsers cannot:- Access another organization.- Change permissions without authorization.- Modify audit records.---## InvitationsUsers cannot:- Create invitations outside their organization.- Reuse expired invitations.---# Audit EventsRequired events:```user.createduser.inviteduser.accepted_invitationuser.updateduser.role.changeduser.suspendedteam.createdteam.member.addedteam.member.removed```---# Future ExtensionsPlanned:- Employee profiles.- Skills.- Certifications.- Availability.- Scheduling.- Performance metrics.- AI coaching profiles.---# Migration OrderDatabase creation order:```1. users2. teams3. team_members4. user_invitations5. user_preferences```---# Acceptance CriteriaDatabase design is complete when:- Users belong to organizations.- Teams can group users.- Invitations work securely.- Preferences support AI personalization.- Tenant isolation is enforced.- Audit events can be generated.---# Next Document**USER-003 — Users &
