# DB-003 — Organizations Entity Relationship Diagram (ERD)**Document ID:** DB-003**Version:** 1.0**Status:** Approved**Owner:** Atlas Engineering**Depends On:**- DB-001 – Atlas Domain Model- DB-002 – Organizations Data Dictionary---# PurposeThis document defines the relationships between the `organizations` table and every entity that depends on it.It establishes the ownership hierarchy for Atlas's multi-tenant architecture.Every business record must belong to exactly one organization.---# Architecture PrincipleOrganization is the root aggregate.```Organization        │        ├──────── Users        │        ├──────── Teams        │        ├──────── Roles        │        ├──────── Customers        │        ├──────── Properties        │        ├──────── Claims        │        ├──────── Documents        │        ├──────── Photos        │        ├──────── Tasks        │        ├──────── AI Sessions        │        ├──────── Supplements        │        ├──────── Reports        │        ├──────── Notifications        │        ├──────── Integrations        │        └──────── Audit Logs```---# Primary Relationships## Organization → UsersRelationship```Organization (1)        │        ▼Users (Many)```Foreign Key```users.organization_id```Delete Behaviour- Restrict deletion- Archive organization instead---## Organization → TeamsRelationship```Organization↓Teams```Foreign Key```teams.organization_id```---## Organization → RolesRelationship```Organization↓Roles```Foreign Key```roles.organization_id```---## Organization → CustomersRelationship```Organization↓Customers```Foreign Key```customers.organization_id```---## Customer → Properties```Customer↓Properties```One customer may own many properties.---## Property → Claims```Property↓Claims```Each property may have multiple insurance claims.---## Claim OwnershipEvery claim belongs to:- one organization- one customer- one propertyOptional relationships include:- adjuster- insurance company- project manager---# Claim Child EntitiesEach claim owns:```Claim├── Documents├── Photos├── Timeline├── Tasks├── AI Sessions├── Evidence Graph├── Supplements├── Compliance Reviews└── Reports```---# Evidence Relationships```Documents        │Photos        │OCR Results        │AI Recommendations        │Supplement Items        │──────────────Evidence Graph```Every AI recommendation should reference supporting evidence.---# AI Relationships```Organization↓Claim↓AI Session↓AI Recommendation↓Human Review```AI never owns business data.It references business data.---# Voice Relationships```Organization↓Users↓Voice Sessions↓Voice Commands↓Voice Actions```Voice sessions reference:- claims- reports- tasks- dashboardsthrough contextual relationships.---# Reporting RelationshipsReports summarize operational data.```Organization↓Reports↓Claims↓Revenue↓Supplements```Reports never duplicate source data.---# Notification RelationshipsNotifications belong to:- organization- userand optionally reference:- claim- task- workflow- AI recommendation---# Audit RelationshipsEvery major entity creates audit events.```User↓Audit Event↓Organization```Audit events are immutable.---# Cardinality Matrix| Parent | Child | Relationship ||---------|-------|--------------|| Organization | Users | 1 : Many || Organization | Teams | 1 : Many || Organization | Roles | 1 : Many || Organization | Customers | 1 : Many || Customer | Properties | 1 : Many || Property | Claims | 1 : Many || Claim | Documents | 1 : Many || Claim | Photos | 1 : Many || Claim | Tasks | 1 : Many || Claim | AI Sessions | 1 : Many || Claim | Supplements | 1 : Many || Claim | Timeline Events | 1 : Many |---# Referential Integrity RulesEvery child entity must:- reference an existing organization- respect tenant boundaries- preserve audit history- prevent orphaned records---# Deletion StrategyAtlas uses soft deletion.Organizations should never be physically deleted.Operational data remains available for:- reporting- auditing- compliance- historical analysis---# Validation ChecklistBefore SQL generation confirm:✓ Every entity has a parent✓ Every relationship has a foreign key✓ Every aggregate has an owner✓ Tenant isolation is preserved✓ Cascade behaviour is documented✓ Audit requirements are satisfied---# Next DocumentDB-004 — Organizations PostgreSQL SchemaThis
