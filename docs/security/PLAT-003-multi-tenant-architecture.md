# PLAT-003 — Atlas Multi-Tenant Architecture & Data Isolation**Document ID:** PLAT-003**Version:** 1.0**Status:** Draft**Owner:** Atlas Engineering**Depends On:**- DB-001 Domain Model- PLAT-001 Authentication Architecture- PLAT-002 Authorization & RBAC---# PurposeThis document defines how Atlas supports multiple organizations while guaranteeing strict separation of customer data.Atlas is a multi-tenant SaaS platform.Each restoration company operates as an independent tenant.---# Multi-Tenant ModelAtlas uses a shared database with logical tenant isolation.Architecture:```                 Atlas Platform                       |              PostgreSQL Database                       | ------------------------------------------------ Organization A        Organization B        Organization C Claims                Claims                Claims Documents             Documents             Documents AI Data               AI Data               AI Data Users                 Users                 Users ------------------------------------------------```---# Tenant DefinitionA tenant is represented by:```organizations.id```Every business record must contain:```organization_id```Example:```claimsidorganization_idcustomer_idclaim_numberstatus```---# Tenant Ownership RuleEvery operational entity belongs to exactly one organization.Required:```organization_id UUID NOT NULL```Required for:- Users- Teams- Customers- Properties- Claims- Documents- Photos- Supplements- Workflows- AI Sessions- Reports- Notifications- Integrations- Audit Logs---# Request Tenant ResolutionEvery incoming request follows:```HTTP Request↓Authentication↓Identify User↓Load Organization Context↓Verify Permission↓Execute Operation```The organization context becomes:```typescript{ userId, organizationId, role, permissions}```---# Data Access RulesAll database queries must include tenant filtering.Incorrect:```sqlSELECT *FROM claims;```Correct:```sqlSELECT *FROM claimsWHERE organization_id = :organizationId;```---# Repository RequirementRepositories must receive organization context.Example:```typescriptclaimsRepository.findAll({ organizationId});```Repositories must never query tenant-owned data without organization context.---# Database ProtectionAtlas should implement PostgreSQL Row Level Security (RLS).Purpose:Provide database-level protection even if application code contains an error.Example:```Application Layer        |Repository Layer        |Database RLS Policy        |PostgreSQL```---# Row Level Security ConceptExample:A claim row:```claim_id:123organization_id:ABC```User belongs to:```organization_id:XYZ```Result:```ACCESS DENIED```---# Storage IsolationFiles require tenant isolation.Storage structure:```/organizations/    /organization-id/        /documents/        /photos/        /exports/        /voice/```Never store files in shared public paths.---# AI Data IsolationAI systems must respect tenant boundaries.AI context:```User↓Organization↓Claim↓Evidence↓AI Reasoning```The AI layer must never receive:- Another organization's documents.- Another organization's claims.- Another organization's conversations.---# Voice IsolationVoice requests must resolve:```Voice Identity↓User↓Organization↓Permissions↓Allowed Data```Example:"Atlas, summarize our active claims."Atlas must know:"our" means the authenticated user's organization.---# Caching RulesCaching must include tenant context.Unsafe:```claims:list```Safe:```organization:A:claims:list```---# Search IsolationSearch indexes must contain tenant identifiers.Example:```{ documentId, organizationId, content}```Search queries must filter:```organizationId = currentOrganization```---# Background JobsEvery job must contain tenant context.Example:Incorrect:```json{ job:"generateSupplement"}```Correct:```json{ job:"generateSupplement", organizationId:"abc123", claimId:"xyz789"}```---# API Security RequirementsEvery endpoint handling tenant data must:- Require authentication.- Resolve organization context.- Validate permissions.- Filter by organization.- Log access.---# Audit RequirementsTenant-sensitive events:- Data access.- Permission changes.- Exports.- AI queries.- Voice commands.- Document downloads.must be recorded.---# Future Scaling StrategyCurrent:```Shared Database+Tenant Isolation```Future enterprise options:```Shared DatabaseorDedicated Database Per Enterprise Tenant```The architecture should support both.---# Security Testing RequirementsTests must verify:- Tenant A cannot access Tenant B data.- API endpoints reject cross-tenant requests.- Storage paths are isolated.- AI context cannot leak data.- Search cannot return other tenant results.---# Acceptance CriteriaMulti-tenancy is complete when:- Every entity has organization ownership.- Every query enforces tenant filtering.- Storage is isolated.- AI respects tenant boundaries.- Voice respects tenant boundaries.- Background jobs carry tenant context.- Cross-tenant access tests pass.---# Next
