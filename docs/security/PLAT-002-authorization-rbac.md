# PLAT-002 — Atlas Authorization & Role-Based Access Control (RBAC)**Document ID:** PLAT-002**Version:** 1.0**Status:** Draft**Owner:** Atlas Engineering**Depends On:**- PLAT-001 Authentication Architecture- DB-001 Domain Model---# PurposeThis document defines the authorization architecture for Atlas.Authentication answers:"Who are you?"Authorization answers:"What are you allowed to do?"Atlas uses Role-Based Access Control (RBAC) to manage permissions across organizations, users, workflows, AI capabilities, and data access.---# Authorization PrinciplesAtlas authorization follows these principles:- Least privilege by default.- Organization isolation is mandatory.- Permissions are explicit.- AI actions require permission validation.- Human approval is required for high-impact actions.- Roles are configurable per organization.---# Authorization ModelAtlas uses:```User |Role |Permissions |Resources |Actions```Example:```Melissa |Owner Role |claims.readclaims.updatesupplements.approve |Claim Records |Allowed Actions```---# Core Entities## RoleA collection of permissions assigned to users.Examples:- Organization Owner- Administrator- Claims Manager- Estimator- Project Manager- Technician- Supplement Specialist- Viewer---## PermissionA specific allowed action.Format:```resource.action```Examples:```claims.readclaims.updatedocuments.uploadsupplements.approveai.executevoice.command```---## User Role AssignmentUsers may have:- One primary role.- Multiple additional roles (future).Example:```User↓Claims Manager+Supplement Specialist```---# Default Atlas Roles## Organization OwnerFull organization access.Permissions:```*```---## AdministratorPlatform management.Allowed:- Manage users.- Manage roles.- Configure settings.- View reports.---## Claims ManagerResponsible for claim operations.Permissions:```claims.readclaims.createclaims.updatedocuments.readdocuments.managephotos.readworkflow.manage```---## EstimatorResponsible for estimates and supplements.Permissions:```claims.readdocuments.readsupplements.createsupplements.updateestimates.manage```---## Project ManagerResponsible for execution.Permissions:```claims.readtasks.manageworkflow.managedocuments.readphotos.manage```---## TechnicianField operations.Permissions:```tasks.readphotos.uploaddocuments.uploadclaim.notes.create```---## Supplement SpecialistRevenue recovery role.Permissions:```supplements.readsupplements.createsupplements.updatesupplements.submitevidence.manage```---## ViewerRead-only access.Permissions:```claims.readdocuments.readreports.read```---# Permission Categories## Organization```organization.readorganization.updateorganization.settings```---## Users```users.readusers.createusers.updateusers.delete```---## Claims```claims.readclaims.createclaims.updateclaims.delete```---## Documents```documents.readdocuments.uploaddocuments.deletedocuments.share```---## Photos```photos.readphotos.uploadphotos.annotatephotos.delete```---## Supplements```supplements.readsupplements.createsupplements.updatesupplements.submitsupplements.approve```---## Compliance```compliance.readcompliance.runcompliance.override```---## AIAI permissions are separated because AI can perform business actions.```ai.queryai.generateai.recommendai.execute```---## VoiceVoice permissions:```voice.accessvoice.commandvoice.execute_action```---# AI Safety RulesAtlas AI must check permissions before:- Generating supplements.- Changing claim data.- Sending communications.- Creating tasks.- Approving recommendations.Example:User:"Atlas, submit this supplement."System checks:```User Identity↓Organization↓Role↓Permission:supplements.submit↓Action Allowed```---# Resource-Level PermissionsFuture versions support granular access.Example:A project manager may access:```Claim AClaim BClaim C```but not:```Claim D```---# Authorization MiddlewareEvery protected request passes through:```Request↓Authentication↓Organization Context↓Permission Check↓Controller↓Service```---# Database RequirementsAuthorization requires:Tables:```rolespermissionsrole_permissionsuser_roles```Relationships:```Organization    | Users    | Roles    | Permissions```---# Audit RequirementsAuthorization events must be logged:- Permission denied.- Role changed.- User added.- User removed.- Privilege escalation attempted.---# Voice AuthorizationVoice-first Atlas requires additional checks.Example:User:"Atlas, show me all claims with missing evidence."Validation:```Voice Identity↓User↓Organization↓claims.read permission↓AI Query Execution```---# Future EnhancementsPlanned:- Attribute-Based Access Control (ABAC).- Department permissions.- Branch-level permissions.- Temporary permissions.- Approval workflows.- External collaborator access.---# Acceptance CriteriaAuthorization is complete when:- Users receive roles.- Roles contain permissions.- Permissions are enforced.- Organizations remain isolated.- AI respects access rules.- Voice commands respect access rules.- Sensitive actions require appropriate privileges.---# Next Document**PLAT-003 — Multi-Tenant Architecture & Data
