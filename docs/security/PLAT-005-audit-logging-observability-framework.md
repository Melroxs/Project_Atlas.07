# PLAT-005 — Atlas Audit Logging & Observability Framework**Document ID:** PLAT-005**Version:** 1.0**Status:** Draft**Owner:** Atlas Engineering**Depends On:**- PLAT-001 Authentication Architecture- PLAT-002 Authorization & RBAC- PLAT-003 Multi-Tenant Architecture- PLAT-004 Error Handling Framework---# PurposeThis document defines how Atlas records, monitors, and analyzes system activity.Audit logging provides accountability.Observability provides operational visibility.Together they allow Atlas to answer:- What happened?- Who performed the action?- When did it happen?- Why did it happen?- What data influenced the decision?---# PrinciplesAtlas observability follows these principles:- Every important business action is traceable.- Audit records are immutable.- AI decisions are explainable.- Security events are captured.- Tenant boundaries are preserved.- Logs never expose sensitive data.---# Three Observability LayersAtlas uses three complementary systems.```                 Atlas Observability                         |        ---------------------------------        Audit Logs     Application Logs     Metrics        ---------------------------------```---# Layer 1 — Audit LoggingPurpose:Track business and security events.Examples:- User created claim.- Document uploaded.- Supplement generated.- AI recommendation approved.- Permission changed.---# Layer 2 — Application LoggingPurpose:Track technical execution.Examples:- API requests.- Database errors.- Background jobs.- Integration failures.---# Layer 3 — MetricsPurpose:Measure system health.Examples:- API response time.- AI processing duration.- Failed workflows.- Queue depth.---# Audit Event ModelEvery audit event contains:```typescript{ id, organizationId, userId, action, entityType, entityId, metadata, timestamp}```---# Audit EntityPrimary table:```audit_logs```Required fields:| Field | Description ||-|-|| id | Unique identifier || organization_id | Tenant owner || user_id | Actor || action | Performed action || entity_type | Resource affected || entity_id | Resource identifier || metadata | Additional context || created_at | Event timestamp |---# Audit ActionsActions follow:```resource.action```Examples:```claim.createdclaim.updateddocument.uploadedsupplement.generatedai.recommendation.createduser.permission.changedvoice.command.executed```---# Business Audit EventsThe following must always be logged.---## Claims```claim.createdclaim.updatedclaim.status.changedclaim.closed```---## Documents```document.uploadeddocument.processeddocument.deleted```---## Photos```photo.uploadedphoto.annotatedphoto.deleted```---## Supplements```supplement.createdsupplement.submittedsupplement.approvedsupplement.rejected```---## AIAI events require additional detail.Required:```ai.request.createdai.response.generatedai.recommendation.createdai.recommendation.approvedai.recommendation.rejected```---# AI Decision AuditEvery AI recommendation must record:```AI Input↓Evidence Used↓Reasoning Summary↓Recommendation↓Confidence Score↓Human Decision```Example:```Recommendation:Add missing roof replacement line itemEvidence:Inspection photosAdjuster notesPolicy documentConfidence:87%Human Decision:Approved```---# Voice AuditEvery voice interaction that performs an action must be recorded.Example:User:"Atlas, create a supplement."Audit:```voice.command.executedAction:supplement.createUser:John SmithOrganization:ABC RestorationResult:Created```---# Security EventsRequired events:```login.successlogin.failedlogoutpassword.changedmfa.enabledmfa.disabledpermission.deniedsession.revoked```---# Logging RulesNever log:- Passwords.- Authentication tokens.- API secrets.- Full claim documents.- Private customer information unnecessarily.---# Request CorrelationEvery request receives:```requestId```Example:```API RequestrequestId:abc-123        |Database Logs        |AI Logs        |Audit Logs```This allows complete tracing.---# MetricsAtlas should monitor:## Platform- API latency.- Error rate.- Availability.---## AI- Generation time.- Confidence scores.- Failed requests.- Human override rate.---## Claims- Claims processed.- Supplement recovery.- Workflow completion.---## Voice- Commands processed.- Successful actions.- Failed commands.---# AlertingCritical alerts:- Database unavailable.- Authentication failures spike.- AI service unavailable.- Storage failure.- Queue failure.---# Data RetentionAudit logs should support:- Organization retention policies.- Regulatory requirements.- Enterprise retention periods.Audit records should generally not be modified after creation.---# Future EnhancementsPlanned:- Advanced analytics.- Compliance reporting.- AI decision replay.- Security dashboards.- Customer activity exports.---# Acceptance CriteriaThe audit system is complete when:- All important actions are recorded.- AI decisions are traceable.- Voice actions are auditable.- Security events are captured.- Logs support debugging.- Tenant boundaries are enforced.---# Next Document**PLAT-006 — Atlas Event Bus & Domain Events Architecture**This document
