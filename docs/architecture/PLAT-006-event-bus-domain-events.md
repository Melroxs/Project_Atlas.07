# PLAT-006 — Atlas Event Bus & Domain Events Architecture**Document ID:** PLAT-006**Version:** 1.0**Status:** Draft**Owner:** Atlas Engineering**Depends On:**- DB-001 Domain Model- PLAT-005 Audit Logging Framework---# PurposeThis document defines the event-driven architecture used by Atlas.Domain events allow independent modules to communicate without creating tightly coupled dependencies.---# Event-Driven PrinciplesAtlas uses events to:- Notify systems of important business changes.- Trigger automation.- Maintain audit trails.- Start AI workflows.- Update analytics.- Trigger notifications.---# Architecture Overview```                 Atlas Application                         |                  Domain Action                         |                  Domain Event                         |                   Event Bus                         | ------------------------------------------------ AI Engine   Workflow   Notifications   Analytics ------------------------------------------------```---# What Is A Domain Event?A domain event represents something important that happened in Atlas.Examples:```ClaimCreatedDocumentUploadedSupplementGeneratedComplianceCheckCompletedAIRecommendationCreatedVoiceActionExecuted```Events represent facts.They are not commands.---# Commands vs Events## CommandA request to perform an action.Example:```GenerateSupplement```Meaning:"Please generate a supplement."---## EventA record that something happened.Example:```SupplementGenerated```Meaning:"The supplement was generated."---# Event StructureEvery Atlas event follows:```typescript{ eventId: string; eventType: string; organizationId: string; entityType: string; entityId: string; payload: object; createdAt: Date;}```---# Event CategoriesAtlas events are grouped by domain.---# Organization EventsExamples:```OrganizationCreatedOrganizationUpdatedOrganizationArchived```---# User EventsExamples:```UserCreatedUserRoleChangedUserDeactivated```---# Claim EventsExamples:```ClaimCreatedClaimUpdatedClaimStatusChangedClaimClosed```---# Document EventsExamples:```DocumentUploadedDocumentProcessedDocumentClassificationCompleted```---# Photo EventsExamples:```PhotoUploadedPhotoAnalyzedDamageDetected```---# AI EventsExamples:```AIAnalysisStartedAIRecommendationCreatedAIConfidenceCalculatedAIReviewRequired```---# Supplement EventsExamples:```SupplementCreatedSupplementValidatedSupplementSubmittedSupplementApprovedSupplementRejected```---# Compliance EventsExamples:```ComplianceCheckStartedCompliancePassedComplianceFailedComplianceExceptionCreated```---# Voice EventsExamples:```VoiceSessionStartedVoiceCommandReceivedVoiceActionCompleted```---# Event Flow Example## ScenarioA restoration company uploads claim documents.Flow:```DocumentUploaded        |Event Bus        |AI Document Processing        |OCR Completed        |Evidence Graph Updated        |Compliance Check Started        |Notification Sent```---# Event ConsumersModules subscribe to events.Example:```DocumentUploadedSubscribers:AI ServiceCompliance EngineAudit SystemNotification Service```---# Event StorageAtlas should maintain an event history.Recommended table:```domain_events```Fields:| Field | Description ||-|-|| id | Event identifier || organization_id | Tenant || event_type | Event name || entity_type | Resource || entity_id | Resource ID || payload | Event data || created_at | Timestamp |---# Event ReliabilityEvents must support:- Retry.- Failure handling.- Replay.- Monitoring.---# Event Processing PatternRecommended:```Create Event      |Store Event      |Publish Event      |Process Consumers      |Mark Complete```---# Background ProcessingLong-running events should execute asynchronously.Examples:- AI document analysis.- OCR processing.- Large report generation.- Supplement package creation.---# AI IntegrationEvents drive AI workflows.Example:```ClaimCreated↓AI Intake Assistant↓Evidence Collection↓Recommendation Engine↓Human Review```---# Voice IntegrationVoice actions generate events.Example:User:"Atlas, create a task for missing photos."Flow:```VoiceCommandReceived↓Permission Check↓TaskCreated↓NotificationSent```---# Event SecurityEvery event must contain:- organizationId.- User context where applicable.- Permission context.- Audit reference.---# Event VersioningEvents must support versioning.Example:```ClaimCreated.v1ClaimCreated.v2```Old consumers must not break when events evolve.---# Future EnhancementsPlanned:- Distributed event streaming.- External partner integrations.- Customer webhooks.- AI agent coordination.- Workflow orchestration.---# Acceptance CriteriaThe event architecture is complete when:- Modules communicate through events.- Business actions create events.- Events are auditable.- Failed events can retry.- AI workflows can trigger automatically.- New modules can subscribe without changing existing modules.---# Next Document**PLAT-007 — Background Jobs & Workflow Processing Architecture**This will define how Atlas handles long-running processes such as OCR, AI
